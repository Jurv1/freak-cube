# Roblox monorepo

Несколько независимых игр Roblox в одном репозитории. Общий код — в `packages/`, каждая игра — в `games/<имя>/`.

## Структура

```
games/<имя>/
  CLAUDE.md              контекст конкретной игры — читай перед работой над ней
  default.project.json   проект Rojo
  docs/design.md         дизайн-документ (пишет агент game-designer)
  src/server             -> ServerScriptService.Server
  src/client             -> StarterPlayerScripts.Client
  src/shared             -> ReplicatedStorage.Shared
packages/                -> ReplicatedStorage.Packages, общий код для всех игр
games/_template/         шаблон новой игры, не игра
```

Игры не импортируют код друг друга. Если что-то нужно двум играм — переноси в `packages/`.

## Команды

Запускаются из корня репо, `<имя>` — папка игры.

```
rojo serve games/<имя>/default.project.json          # живая синхронизация в Studio
rojo build games/<имя>/default.project.json -o build/<имя>.rbxl
stylua games/<имя>/src packages                      # форматирование
selene games/<имя>/src packages                      # линтер
```

После любой правки `.luau` запусти `stylua` и `selene` по затронутой игре и исправь замечания до того, как сообщать о готовности.

### Тулчейн

`rojo`, `stylua` и `selene` ставит Rokit, версии закреплены в `rokit.toml`. На новой машине: установить Rokit, затем `rokit install` в корне репо. Обновлять версии — там же, не ставить инструменты мимо Rokit.

Если команда не находится, в PATH этой сессии нет `~/.rokit/bin` — вызывай по полному пути (`~/.rokit/bin/rojo.exe`).

Ошибка `Failed to find tool 'rojo' in any project manifest file` значит, что команда запущена не из папки репо: Rokit ищет `rokit.toml` в текущей папке и выше. Когда даёшь пользователю команду, указывай папку.

### Синхронизация с Studio

Правки из файлов попадают в Studio, только пока запущен `rojo serve` и в плагине Rojo в Studio нажато Connect. Это делает пользователь, и между сессиями оно не сохраняется — не предполагай, что синхронизация идёт, а проверяй: прочитай изменённый скрипт через `script_read` и сравни с файлом.

Если синхронизации нет и пользователь не может её включить, повтори ту же правку в Studio через `multi_edit` и сверь исходники. Раскладка в Studio повторяет проект Rojo (`ServerScriptService.Server`, `StarterPlayerScripts.Client`, `ReplicatedStorage.Shared`), поэтому подключение Rojo не создаёт дубли скриптов.

## Источник правды: файлы, а не Studio

- **Код** живёт только в файлах репо и попадает в Studio через Rojo. Не правь скрипты через Studio MCP (`multi_edit`): Rojo перезапишет их при следующей синхронизации, и правка потеряется.
- **Всё, что не код** (карта, модели, GUI, освещение), живёт в place-файле в Studio. Это можно менять через Studio MCP, но сначала скажи пользователю, что именно меняешь: в git этих изменений не будет, откатить их можно только через Ctrl+Z в Studio.

## Проверка в Studio

Подключён MCP-сервер Roblox Studio. Статические проверки (`selene`) не ловят ошибки времени выполнения, поэтому изменение поведения считается проверенным только после запуска в Studio — процедура в скилле `studio-check`. Если Studio не открыта или открыто не то место, скажи об этом прямо, а не пиши «должно работать».

## Соглашения Luau

- Файлы `.luau`, в начале каждого — `--!strict`. Типы ловят ошибки, которые иначе видны только в Studio.
- `task.wait` / `task.spawn` / `task.delay` вместо `wait` / `spawn` / `delay`: старые функции троттлятся и устарели.
- Сервисы получай через `game:GetService("…")`, в начале файла.
- Именование: `PascalCase` для модулей, типов и сервисов; `camelCase` для локальных переменных и функций; `UPPER_SNAKE` для констант.
- Суффиксы файлов Rojo: `*.server.luau` — Script, `*.client.luau` — LocalScript, остальные — ModuleScript.

## Безопасность: клиенту не доверяем

Любой клиент может вызвать любой ремоут с любыми аргументами — эксплойты в Roblox массовые.

- Сервер проверяет тип и диапазон каждого аргумента ремоута и право игрока на действие (дистанция, кулдаун, владение предметом).
- Валюта, инвентарь, прогресс и урон считаются только на сервере. Клиент присылает намерение («хочу купить X»), а не результат («у меня теперь 500 монет»).
- На каждый ремоут — ограничение частоты вызовов.
- Покупки за Robux выдаются только из `MarketplaceService.ProcessReceipt`, и обработчик идемпотентен: один и тот же чек может прийти повторно.

## Данные игроков

- Сохранение через DataStore — с `pcall`, повторами и сохранением в `BindToClose`. Потеря прогресса — худший баг для удержания.
- Меняешь формат сохранения — добавляй миграцию со старого формата, у живых игроков данные уже лежат в старом.

## Дизайн и монетизация

Механики, прогрессию, экономику и монетизацию проектирует агент `game-designer`. Он пишет `games/<имя>/docs/design.md`; при реализации сверяйся с этим документом, а расхождения выноси на обсуждение, а не решай молча.
